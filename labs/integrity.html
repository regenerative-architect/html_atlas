    More worked examples

    Three uses of a plain SHA-256 digest for proving something has not changed, without any external verification service.

    Hashing content to get a short, comparable fingerprint

    The same digest function this atlas’s own SHA256SUMS.json was generated with: a small, fixed-length fingerprint that changes completely if even one character of the input changes.

    async function digestOf(text){
  const bytes=await crypto.subtle.digest('SHA-256',new TextEncoder().encode(text));
  return [...new Uint8Array(bytes)].map(b=>b.toString(16).padStart(2,'0')).join('');
}

    Expected outcome: digestOf("hello") always returns the same 64-character string; changing the input by one character produces a completely different one, not a similar one.

    Detecting drift against a known-good hash

    Recording a document’s hash at publish time, then recomputing it later, is a way to detect — offline, with no server round trip — whether that specific content has been altered since.

    async function detectDrift(currentText,knownGoodHash){
  return (await digestOf(currentText))===knownGoodHash;
}

    Extend it: store the known-good hash somewhere the content itself cannot modify (a separate signed manifest file, as this atlas does), or the check can be defeated by editing both together.

    Chaining records so tampering with history is detectable

    Each record’s hash folds in the previous record’s hash, the same core idea behind a blockchain’s tamper-evidence: editing an old record changes its hash, which no longer matches what the next record chained against.

    async function chainRecord(previousHash,record){
  const payload=previousHash+JSON.stringify(record);
  const hash=await digestOf(payload);
  return {...record,prevHash:previousHash,hash};
}

    Expected outcome: replaying the chain and recomputing each hash from its stored prevHash and content will mismatch at exactly the point where a record was altered, pinpointing where history was changed.
